# Reply Routing: First Top-Level, Then Threaded — Design

**Status:** Draft for review
**Date:** 2026-05-28
**Author:** infrabot (with refinements from devbot and approval from sherod)
**Repo:** `sherodtaylor/claude-code-channel-matrix`

---

## Problem

Today the `reply` MCP tool sets `m.relates_to.rel_type=m.thread` on **every**
call where `reply_to_event_id` is provided
(`plugins/matrix-channel/server.ts:1088-1099`, `buildMessageBody` at
`server.ts:414-438`). Following the `matrix:threading` skill's prescription
to "pass the inbound `event_id` as `reply_to_event_id` on every reply,"
the agent threads its *first* reply too — which means:

- The first reply (the actual answer / wake-up message) lands inside a
  thread sidebar, not in the room's main timeline.
- Threaded-mode Element clients hide it behind a thread bubble that the
  user has to expand to read.
- The user perceives the bot as silent or unresponsive.

Observed concretely on this session: replies to messages
`$DYbJcGCd…` and `$7vyj92CXYOAFO…` had `ok:true` server acceptance
but no replies visible in the main timeline.

We also have a related msgtype problem in the reply path: every reply
currently goes out as `m.text` (PR #4), which always push-notifies the
recipient. For threaded *follow-up* narration we want quiet (`m.notice`);
for top-level wake-ups we still want loud (`m.text`).

## Goal

Make the plugin route replies correctly without making the agent track
per-event state. Both the threading routing and the msgtype split are
coupled and ship together — shipping either alone produces a worse UX
than today.

After this change:

- **First** `reply(..., reply_to_event_id=$X)` per inbound event `$X` →
  posts top-level (no `m.relates_to`) with `msgtype: m.text`. Loud wake-up.
- **Subsequent** `reply(..., reply_to_event_id=$X)` →
  threaded under the **original inbound event** `$X` (not under the bot's
  first reply) with `msgtype: m.notice`. Quiet narration.
- `reply(...)` **without** `reply_to_event_id` → top-level, `msgtype: m.text`,
  routing state untouched.
- Optional `force_top_level: true` → posts top-level, `msgtype: m.text`,
  and **deletes** the routing state entry for that event so the next
  reply restarts the "first → top, then threaded" cycle.

## Architecture

### State

A single in-process Map kept on the server module scope:

```typescript
interface ReplyRoutingEntry {
  firstReplyAt: number  // epoch ms; used for TTL sweep
}
const replyRoutingState = new Map<string, ReplyRoutingEntry>()
const REPLY_ROUTING_TTL_MS = 10 * 60 * 1000  // 10 min
```

Key = the inbound event ID (`reply_to_event_id` argument). Value records
the timestamp at which the bot first replied to that event.

### TTL sweep

On every `reply` call we lazily sweep entries whose `firstReplyAt` is
older than `REPLY_ROUTING_TTL_MS`. No background timer — the map is
expected to stay small (one entry per active conversation in the last
~10 min).

### Routing decision

Inside the `reply` tool handler:

```
1. If args.reply_to_event_id is absent:
     route = TOP_LEVEL, msgtype = 'm.text'
     (do not touch the map; force_top_level is ignored if also absent
      reply_to_event_id, since top-level is already the default)
2. Else if args.force_top_level === true:
     route = TOP_LEVEL, msgtype = 'm.text'
     delete map entry for reply_to_event_id
3. Else if map has an entry for reply_to_event_id (after TTL sweep):
     route = THREADED under reply_to_event_id, msgtype = 'm.notice'
4. Else:
     route = TOP_LEVEL, msgtype = 'm.text'
     set map entry { firstReplyAt: now }
```

### Wire format

- `route = TOP_LEVEL`: `buildMessageBody(text, html)` with no
  `threadRootId`. No `m.relates_to`. `msgtype: m.text`.
- `route = THREADED`: `buildMessageBody(text, html, reply_to_event_id)`.
  Sets `m.relates_to.rel_type=m.thread` with `event_id=reply_to_event_id`,
  `is_falling_back: true`, and `m.in_reply_to`. `msgtype: m.notice`.

The thread root remains the **user's inbound event**, not the bot's
first reply. This keeps Matrix's "thread root = user's message" mental
model intact for clients that surface thread roots in UI.

### Backwards compat

- Callers who set `reply_to_event_id` get the new routing automatically.
  This is the desired correction — old behavior was the bug.
- Callers who don't set `reply_to_event_id` see no change (still
  top-level, still `m.text`).
- The `replyToMode` access setting (`first | all | off`) is orthogonal —
  it gates multi-chunk handling, not first-vs-subsequent routing.
  Multi-chunk replies are not generated by the plugin today.

### MCP tool schema change

Add an optional `force_top_level: boolean` parameter to the `reply`
tool's input schema. Update the tool description to surface the new
auto-routing contract so future agents and the `matrix:threading` skill
stay consistent.

### Skill + instructions update

Update `plugins/matrix-channel/skills/threading/SKILL.md`
to reflect the new contract:

> Pass `reply_to_event_id = <inbound event_id>` on every reply. The
> plugin automatically routes the first reply per inbound event to the
> main timeline (loud) and subsequent replies into a thread under it
> (quiet). Pass `force_top_level: true` to force a fresh top-level
> wake-up after a long stretch of progress narration.

Also update the MCP `instructions` field and remove the now-misleading
guidance that says "Threading is per-call: pass `reply_to_event_id` on
each reply that should be threaded."

## Test plan

New tests in `server.test.ts` (`bun test`):

1. **No `reply_to_event_id` → top-level, map untouched.**
   - Setup: empty map.
   - Call: `reply(room_id, text)`.
   - Assert: outgoing body has no `m.relates_to`, `msgtype=m.text`,
     map size still 0.

2. **First call with `reply_to_event_id` → top-level, map gains entry.**
   - Setup: empty map.
   - Call: `reply(room_id, text, reply_to_event_id=$X)`.
   - Assert: outgoing body has no `m.relates_to`, `msgtype=m.text`,
     map has entry for `$X`.

3. **Second call with same `reply_to_event_id` → threaded under `$X`,
   `m.notice`.**
   - Setup: map has entry for `$X` (from prior call).
   - Call: `reply(room_id, text, reply_to_event_id=$X)`.
   - Assert: outgoing body has
     `m.relates_to.rel_type=m.thread`,
     `m.relates_to.event_id=$X`,
     `m.in_reply_to.event_id=$X`,
     `is_falling_back=true`,
     `msgtype=m.notice`.

4. **TTL expiry resets routing.**
   - Setup: map has entry for `$X` with `firstReplyAt` older than
     `REPLY_ROUTING_TTL_MS`.
   - Call: `reply(room_id, text, reply_to_event_id=$X)`.
   - Assert: routes as fresh first call (top-level, `m.text`),
     `firstReplyAt` updated to now.

5. **`force_top_level=true` posts top-level and resets routing.**
   - Setup: map has entry for `$X`.
   - Call: `reply(room_id, text, reply_to_event_id=$X, force_top_level=true)`.
   - Assert: outgoing body has no `m.relates_to`, `msgtype=m.text`,
     map entry for `$X` is gone.
   - Follow-up call with same `$X` routes as fresh first.

6. **Independent inbound events don't share state.**
   - Setup: map has entry for `$X`.
   - Call: `reply(room_id, text, reply_to_event_id=$Y)`.
   - Assert: top-level (first for `$Y`), map now has both `$X` and `$Y`.

7. **TTL sweep removes only expired entries.**
   - Setup: map has `$X` expired and `$Y` fresh.
   - Call: `reply(room_id, text, reply_to_event_id=$Z)`.
   - Assert: map no longer contains `$X`, still contains `$Y`,
     gained `$Z`.

8. **Tool schema exposes `force_top_level: boolean`.**
   - Assert: `replyToolDefinition.inputSchema.properties.force_top_level`
     exists and has `type: 'boolean'`.

For deterministic testing, the time source (`Date.now`) is injected via
an optional `now: () => number` parameter on the helper that performs
the routing decision (default: `() => Date.now()`). The map is
module-scope but accessible to tests via an exported `__resetReplyRoutingForTest()`
helper (no production caller) and an exported view of the map size for
sweep assertions.

## Migration impact

- **Agents that follow the `matrix:threading` skill** (pass
  `reply_to_event_id` on every reply): now get the intended UX —
  first reply visible in main timeline, follow-ups quiet in a thread.
  No code change required on the agent side.
- **Agents that don't pass `reply_to_event_id`**: unchanged.
- **Edit_message (PR #5)**: unchanged — already `m.notice`.

## Risks and trade-offs

- **State is per-process.** A plugin restart drops the map, so a long
  conversation that crosses a restart will see its next reply route as
  fresh first (top-level + push). Acceptable; this matches the
  "session ended" UX.
- **Memory growth.** Map size grows with active inbound events
  inside the TTL window. For typical workloads (single bot, single
  operator, occasional teammates) this is bounded at ~tens of entries.
  The lazy TTL sweep keeps it tidy.
- **Two msgtypes in flight in the same conversation.** Element handles
  this fine; some niche clients may render `m.notice` differently.
  Already accepted risk per the `m.notice` flip discussion.

## Out of scope

- Typing-indicator heartbeat for long thinking sessions (tracked as
  task #92, separate PR).
- Multi-chunk reply routing (the `replyToMode` access knob already
  exists and is independent).
- Threading reactions (`react` tool is unaffected).
- Cross-process state (no Redis, no file persistence).
